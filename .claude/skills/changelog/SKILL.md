调用此 skill 时：

1. **读取参数**确定目标版本或冲刺编号。如给定版本，使用相应的 git 标签。如给定冲刺编号，使用冲刺日期范围。

1b. **检查 git 可用性**——验证仓库已初始化：
   - 运行 `git rev-parse --is-inside-work-tree` 确认 git 可用
   - 如非 git 仓库，通知用户并优雅中止

2. **读取 git 日志**自上次标签或发布以来：
   ```
   git log --oneline [上次标签]..HEAD
   ```
   如无标签，读取完整日志或合理的最近范围（最近 100 次提交）。

3. **读取冲刺报告**从 `production/sprints/` 中获取相关时期的计划工作和变更上下文。

4. **读取已完成的设计文档**从 `design/gdd/` 中获取在此期间实现的任何新功能。

5. **将每个变更分类**到以下类别之一：
   - **新功能**：全新的游戏系统、模式或内容
   - **改进**：对现有功能的增强、UX 改进、性能提升
   - **Bug 修复**：对破坏行为的修正
   - **平衡变更**：游戏数值、难度、经济的调整
   - **已知问题**：团队已知但尚未解决的问题

6. **生成内部更新日志**（完整技术细节）：

```markdown
# 内部更新日志：[版本]
日期：[日期]
冲刺：[包含的冲刺编号]
提交：[数量]（[首次hash]..[末次hash]）

## 新功能
- [功能名称] -- [技术描述，受影响的系统]
  - 提交：[hash1]、[hash2]
  - 负责人：[实现者]
  - 设计文档：[链接如适用]

## 改进
- [改进] -- [技术上改了什么以及为什么]
  - 提交：[hashes]
  - 负责人：[谁]

## Bug 修复
- [BUG-ID] [bug 描述及根因]
  - 修复：[改了什么]
  - 提交：[hashes]
  - 负责人：[谁]

## 平衡变更
- [调整了什么] -- [旧值 -> 新值] -- [设计意图]
  - 负责人：[谁]

## 技术债务 / 重构
- [清理了什么以及为什么]
  - 提交：[hashes]

## 已知问题
- [问题描述] -- [严重程度] -- [预计修复时间如已知]

## 指标
- 总提交数：[N]
- 文件变更数：[N]
- 添加行数：[N]
- 删除行数：[N]
```

7. **生成面向玩家的更新日志**（友好、非技术性）：

```markdown
# [版本] 更新内容

## 新功能
- **[功能名称]**：[面向玩家的描述，说明他们现在能做什么、为什么令人兴奋。聚焦体验，而非实现。]

## 改进
- **[改进了什么]**：[这对玩家有什么好处。具体但避免术语。]

## Bug 修复
- 修复了 [描述玩家经历了什么，而非代码出了什么问题]
- 修复了 [玩家可见的症状]

## 平衡变更
- [玩家可理解的变更和设计意图。示例："治疗药水现在恢复 50 HP（原为 30）——我们觉得玩家在后期遭遇中需要更多恢复选项。"]

## 已知问题
- 我们已知 [玩家角度的描述] 并正在修复。[如有的解决方案。]

---
感谢游玩！你的反馈帮助我们让游戏变得更好。
报告问题请至 [链接]。
```

8. **向用户输出两份更新日志**。内部更新日志是主要工作文档。面向玩家的更新日志经审查后即可发布到社区。

### 准则

- 绝不在面向玩家的更新日志中暴露内部代码引用、文件路径或开发者名称
- 将相关变更分组而非列出独立提交
- 如提交信息不清晰，检查相关文件和冲刺数据获取上下文
- 平衡变更应始终包含设计理由，而非仅有数字
- 已知问题应诚实——玩家欣赏透明度
- 如 git 历史混乱（合并提交、回退、修正提交），清理叙述而非逐字列出每个提交
