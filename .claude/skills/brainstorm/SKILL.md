调用此 skill 时：

1. **解析参数**获取可选的类型/主题提示（如 `roguelike`、`space survival`、`cozy farming`）。如为 `open` 或无参数，从头开始。

2. **检查现有概念工作**：
   - 如存在，阅读 `design/gdd/game-concept.md`（恢复而非重启）
   - 如存在，阅读 `design/gdd/game-pillars.md`（在已有支柱上构建）

3. **交互式运行构思阶段**，在每个阶段向用户提问。不要静默生成一切——目标是**协作式探索**，AI 充当创意引导者，而非人类愿景的替代品。

   **在构思过程中的关键决策点使用 `AskUserQuestion`**：
   - 约束性品味问题（类型偏好、范围、团队规模）
   - 概念选择（在呈现选项后："哪 2-3 个概念让你有共鸣？"）
   - 方向选择（"进一步开发、继续探索，还是制作原型？"）
   - 概念细化后的支柱排序
   先在对话文本中撰写完整的创意分析，然后使用 `AskUserQuestion` 捕获决策。

   遵循专业工作室构思原则：
   - 暂缓评判——探索期间没有坏想法
   - 鼓励不寻常的想法——跳出框架的思考激发更好的概念
   - 互相建设——"是的，而且……"的回应，而非"但是……"
   - 用约束作为创意燃料——限制往往产生最好的想法
   - 每个阶段限时——保持势头，不要在早期过度纠结

### 阶段 1：创意发现

从理解人开始，而非游戏。以对话方式（非清单式）提出以下问题：

**情感锚点**：
- 游戏中有没有一个时刻真正打动了你、让你激动或让你忘记了时间？具体是什么创造了那种感觉？
- 有没有你一直想在游戏中拥有但从未找到的幻想或权力体验？

**品味特征**：
- 你花最多时间玩的 3 款游戏是什么？是什么让你持续回来玩？
- 有没有你喜欢的类型？你回避的类型？为什么？
- 你更喜欢挑战你、放松你、给你讲故事，还是让你表达自己的游戏？

**实际约束**（在构思前塑造游戏的边界）：
- 独立开发者还是团队？有哪些可用技能？
- 时间线：数周、数月还是数年？
- 是否有平台约束？（仅 PC？移动端？主机？）
- 第一款游戏还是有经验的开发者？

**综合**答案形成**创意简报**——3-5 句话总结用户的情感目标、品味特征和约束条件。回读简报并确认它捕获了意图。

---

### 阶段 2：概念生成

以创意简报为基础，生成 **3 个不同的概念**，每个采取不同的创意方向。使用以下构思技巧：

**技巧 1：动词优先设计**
从核心玩家动词开始（建造、战斗、探索、解决、生存、创造、管理、发现）并从那里向外构建。动词就是游戏。

**技巧 2：混搭方法**
组合两个意想不到的元素：[类型 A] + [主题 B]。两者之间的张力创造独特卖点。（如"种田模拟 + 宇宙恐怖"、"roguelike + 约会模拟"、"城市建造 + 实时战斗"）

**技巧 3：体验优先设计（MDA 反向）**
从期望的玩家情感（MDA 框架中的美学目标：感觉、幻想、叙事、挑战、社交、探索、表达、沉浸）开始，逆向推导产生它们的动态和机制。

为每个概念呈现：
- **工作标题**
- **电梯演讲**（1-2 句话——必须通过"10 秒测试"）
- **核心动词**（最常出现的单一玩家操作）
- **核心幻想**（情感承诺）
- **独特卖点**（通过"而且还有"测试："像 [可比游戏]，**而且还有** [独特之处]"）
- **主要 MDA 美学**（哪种情感占主导？）
- **预估范围**（小 / 中 / 大）
- **为什么可能成功**（1 句话关于市场/受众契合度）
- **最大风险**（1 句话关于最难回答的未解问题）

呈现所有三个。请用户选择一个、组合元素或请求新概念。永远不要施压选择——让他们仔细考虑。

---

### 阶段 3：核心循环设计

对选定的概念，使用结构化提问构建核心循环。核心循环是游戏的心脏——如果单独玩都不有趣，再多的内容或打磨也救不了游戏。

**30 秒循环**（时时刻刻）：
- 玩家最常做的实际操作是什么？
- 这个操作本身令人满足吗？（没有奖励、没有进度、没有故事——仅凭感觉他们也会做吗？）
- 什么让这个操作感觉好？（音频反馈、视觉果汁、时机满足感、战术深度？）

**5 分钟循环**（短期目标）：
- 什么将时时刻刻的玩法组织成循环？
- "再来一回合"/"再来一局"的心理在哪里触发？
- 玩家在这个层面做出什么选择？

**单次会话循环**（30-120 分钟）：
- 一次完整的游戏会话是什么样子？
- 自然的停止点在哪里？
- 什么"钩子"让他们在不玩游戏时还想着它？

**进度循环**（数天/数周）：
- 玩家如何成长？（力量？知识？选项？故事？）
- 长期目标是什么？游戏何时"完成"？

**玩家动机分析**（基于自我决定理论）：
- **自主性**：玩家有多少有意义的选择？
- **胜任感**：玩家如何感受自己的技能在成长？
- **关联性**：玩家如何感到连接（与角色、其他玩家或世界）？

---

### 阶段 4：支柱和边界

游戏支柱被真实 AAA 工作室（《战神》、《Hades》、《最后生还者》）用于让数百名团队成员做出方向一致的决策。即使对独立开发者，支柱也能防止范围蔓延并保持愿景清晰。

协作定义 **3-5 个支柱**：
- 每个支柱有**名称**和**一句话定义**
- 每个支柱有**设计测试**："如果我们在 X 和 Y 之间辩论，这个支柱说我们选择 __"
- 支柱之间应该产生张力——如果所有支柱都指向同一方向，它们没有发挥足够的作用

然后定义 **3+ 个反支柱**（这个游戏不是什么的）：
- 反支柱防止最常见的形式——"如果……会很酷"——那些不服务于核心愿景的功能
- 表述为："我们**不会**做 [某事物]，因为它会损害 [支柱]"

---

### 阶段 5：玩家类型验证

使用 Bartle 分类法和 Quantic Foundry 动机模型，验证这个游戏实际是为谁做的：

- **主要玩家类型**：谁会爱上这个游戏？（成就者、探索者、社交者、竞争者、创造者、故事讲述者）
- **次要吸引力**：还有谁可能享受它？
- **不适合谁**：清楚地知道谁不会喜欢这个游戏与知道谁会喜欢同样重要
- **市场验证**：是否有服务类似玩家类型的成功游戏？从它们的受众规模中我们能学到什么？

---

### 阶段 6：范围和可行性

将概念落地到现实中：

- **引擎推荐**（Godot / Unity / Unreal）附基于概念需求、团队专业知识和平台目标的推理
- **美术管线**：美术风格是什么，劳动密集程度如何？
- **内容范围**：估算关卡/区域数量、物品数量、游戏时长
- **MVP 定义**：测试"核心循环有趣吗？"的绝对最小构建是什么？
- **最大风险**：技术风险、设计风险、市场风险
- **范围层级**：完整愿景 vs 如果时间不够时发布什么？
